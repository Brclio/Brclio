# 小红书下载器的新旧客户端对照

2026-11-26 在同一台 Apple Silicon Mac 上核查。旧下载器为用户指定仓库的 2.0.36（工作树 `eb346dd`），Brclio 修复前基线为 0.2.10（`1ef0fa8`）。旧仓库自 2.0.36 标签以来增加了迁移工具，原桌面媒体下载实现没有变化。此次比较的是安装在电脑上的下载器工作流，同时核对了 Android 单篇入口。

## 哪些操作会变慢

| 操作 | 对照结果 |
| --- | --- |
| 解析后直接点「下载所选视频」 | 旧版默认选推荐播放清晰度，Brclio 0.2.10 默认选原视频，预览也跟着选原视频。现已恢复普通下载的默认选择，原视频仍可手选，只有原视频时直接选它。旧项目记录过同一篇的原文件为 260,311,194 字节、默认播放版为 26,681,111 字节，前者约 9.76 倍。这是历史样本的文件大小。 |
| 明确选同一个视频文件 | 同一份 23,916,885 字节 H.264/AAC 文件，用真实 Electron 44.6.0、同一本机 HTTPS 服务、各自的原生视频下载器及请求适配器。每版预热一次，交错测试六次。在 16 MiB/s 限速下，旧版中位 1.442 秒、Brclio 1.439 秒；本机不限速时分别为 0.101 秒和 0.096 秒。独立复跑 16 MiB/s 场景，中位数分别为 1.442 秒和 1.445 秒。每次只取一次文件，最终字节摘要和媒体轨道均通过。 |
| 主页列表正在翻页 | 设请求间隔 10 秒、随机延迟 0，构造同一页在第 4 秒完成加载的事件序列。旧版在第 12.2 秒确认末尾；Brclio 0.2.10 使用等待前的加载状态，又等了一轮，到第 22.2 秒才确认。修复后同样在第 12.2 秒确认。以上为可重复的模拟时钟；另以真实 Electron 与本机 HTTPS 检查了完整列表确认后才开始下载。 |
| 完成发现后，逐篇下载 | 两篇笔记、每篇三图、默认间隔 10 秒及固定 1.5 秒随机延迟时，两版的详情请求均在模拟时钟第 11.5 和 57.5 秒启动，最后一张图均在第 92 秒启动。六张图的文件摘要一致。主页的请求间隔和完整发现后才下载的规则均保留。 |
| 将原图导出为 ZIP | 24 张不同 PNG，每张 768 KiB，使用内存模拟 CDN，加上真实文件系统。Brclio 修复前后各五轮中位数为 399 毫秒和 156 毫秒。前后都是 24 次源请求，逐项 CRC32 和 SHA-256 相符。修复去掉了每张图写暂存文件、同步、再整份读回的过程，共节省 18 MiB 写、18 MiB 读和 24 次文件同步。此数字反映本机打包开销。 |

另用同一个本机 HTTP 源和同一套 Node 请求，在 8 MiB/s 限速下对照旧版原生保存与 Brclio 完整的 `request('saveVideo')`。16 MiB 双轨视频各预热一次、交错测量四次，中位数为旧版 2.045 秒、Brclio 2.051 秒。每次均只有一个 GET，所有落盘文件的 SHA-256 相同。这组测量包含 Brclio 主进程的流包装、进度回调、文件写入和校验。

旧样本的编码、时长与文件身份记录见旧项目的 `docs/watermark-free-video.md`。这次匿名访问同一历史笔记时，旧版和新版均收到到 `www.rednote.com` 的 302 重定向，并按各自的域名规则停止。反馈者尚未提供链接、系统、具体操作或计时，当前没有该用户所在网络的 CDN 吞吐数据。

## 下载功能覆盖

| 工作流 | 核对的行为 |
| --- | --- |
| 单篇解析 | 分享文案、长短链接、原图链接，桌面 Node / Python 切换和失败提示。桌面 Python 不可用时在引擎选择里显示并切回 Node。 |
| 图文 | 查看原图、单张及所选原图保存、图片或文件剪贴板、复制直链、复制文案、TXT 导出、整篇媒体与元信息保存。复制多张图返回文件时明确告知粘贴方式。图片代理缓冲后写盘时，字节进度持续向前。 |
| 视频 | 预览、清晰度选择、普通与原视频、备用源、取消、流式落盘、文件长度和音视频轨道校验。单篇下拉选择作用于预览和「下载所选视频」。整篇和主页归档继续优先保存可用原视频。预览的 HEAD 请求透传给 CDN，遇到不支持 HEAD 的响应才回退 GET。 |
| 所选素材 ZIP | 归档预算包含文案与媒体，低内存桌面按 128 MiB、其余桌面按 256 MiB 检查。原图签名和视频轨道在最终打包前校验。条目失败会显示，取消和超限均保留原目标文件。 |
| 主页批量 | 小红书网页登录及清除会话、选择目录、分页去重、确认末尾、间隔和抖动、队列及失败项、暂停/继续/重试、按编号与标题建目录、重启恢复、已有文件按完整性跳过。 |
| Android 单篇 | 系统分享接收、原图保存/复制/分享、视频选择和备用地址、文案及归档。新分享取代旧草稿后，旧解析结果不能覆盖新笔记。只声明视频却拿不到可保存地址时，整篇入口会报告缺失。 |

### 0.2.11 发布前复核

- **单篇图文**。桌面卡片的「保存原图」可以选择单个文件名，默认编号和扩展名取自图片序号和实际文件格式。批量保存仍可选目录。应用内预览和系统浏览器打开原图都有入口。
- **单篇视频**。普通视频、原视频和同类备用地址分别核对。下载期间可查看已收字节、平均速度和耗时，切换备用地址时重新测算该次传输速度。
- **主页批量**。进入主页页签时检查已有的小红书登录会话，退出页签后丢弃过期的状态回执。失败项可单篇重试、集中重试、复制链接或转入单篇。转入时清空旧结果，活动下载期间保留当前操作。
- **本机诊断**。现有日志记录下载结果、重试及错误码，可在设置中复制。用临时目录验证了连接中断后重试成功的记录，预览文本过滤了原始链接、笔记内容、凭据和路径。

线路也可能影响实测。旧版原生单视频和剪贴板使用 Electron 默认会话，Brclio 的小红书专用会话固定直连。主机启用系统代理或 PAC 时，两者可能走不同链路。本次测试机的 HTTP、HTTPS、SOCKS 和 PAC 开关均关闭。

## 复测入口

首轮速度修复的本机全量测试通过 607 项，跳过 8 项 Windows 专属测试。旧版来源一致性检查通过 61 项，Android 单元测试通过 128 项。界面回归还覆盖了原图文件剪贴板、字节进度、视频预览与实际保存地址，以及 Android 分享交替到达的情况。这组速度测量取自 Mac。

`npm run test:xhs-source-parity` 对用户指定的旧仓库执行 61 项逐字核对。下载器行为另由 `npm run test:xhs`、`npm run test:xhs-desktop`、`npm run test:xhs-redirects`、`npm run test:xhs-profile-discovery`、`npm run test:xhs-ui` 与 `npm run test:xhs-download-ui` 覆盖。Android 的原生策略测试为 `android/gradlew` 下的 `:app:testDebugUnitTest` 任务。

在 Brclio 仓库根目录执行以下命令可用同一脚本复测 ZIP 前后的耗时、额外读写量和归档内每个文件的摘要。各轮具体耗时会随磁盘和系统负载波动。

```sh
baseline_dir=$(mktemp -d)
git archive 1ef0fa8 desktop/xhs | tar -x -C "$baseline_dir"
node scripts/benchmark-xhs-archive.cjs "$baseline_dir"
node scripts/benchmark-xhs-archive.cjs
```
